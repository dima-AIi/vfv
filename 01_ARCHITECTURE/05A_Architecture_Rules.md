1\. Executive Summary

1.1 Назначение документа



05A_Architecture_Rules.md определяет обязательные правила разработки платформы DevOS.



Этот документ является фундаментальным соглашением между:



разработчиками;

AI-агентами;

техническими инструментами;

будущими командами разработки.



Главная задача документа:



Гарантировать, что DevOS останется качественной, масштабируемой и поддерживаемой платформой независимо от количества функций, модулей и участников разработки.



DevOS создается не как одно приложение.



Архитектурная модель:



DevOS Platform Core



&#x20;       +



Reusable Modules



&#x20;       +



Business Configurations



&#x20;       +



Industry Solutions



Поэтому главный архитектурный риск проекта:



не отсутствие функций,



а постепенная потеря архитектурной целостности.



1.2 Проблема, которую решает документ

FACT



Исследования предыдущих документов показали:



большинство бизнес-систем начинают с простого решения;

со временем количество функций увеличивается;

появляются зависимости между компонентами;

код становится сложным для изменения;

автоматизация разработки через AI увеличивает скорость создания кода, но повышает риск архитектурной деградации.



Источники:



03\_Competitor\_Research.md

04\_SaaS\_Research.md

05\_DevOS\_Architecture\_Foundation.md

ANALYSIS



Для DevOS риск выше, чем для обычного SaaS.



Причина:



DevOS предполагает:



множество модулей;

разные бизнес-сценарии;

разные типы клиентов;

длительный жизненный цикл;

развитие в SaaS-платформу.



Без строгих правил через несколько лет система может превратиться в:



Большой монолит



\+



множество исключений



\+



непонятные зависимости



\+



невозможность безопасных изменений

ENGINEERING DECISION



DevOS использует модель:



Architecture Governance First



То есть:



сначала определяются правила,



потом создается код.



Любое техническое решение должно соответствовать Architecture Rules.

Как гарантировать, что через год разработки DevOS останется поддерживаемой платформой?



Ответ:



Через систему ограничений.



DevOS использует принцип:



Свобода разработки



&#x20;       +



Архитектурные ограничения



&#x20;       =



Масштабируемая система

2.2 Что регулирует данный документ

База данных	безопасное развитие модели данных

Документация	сохранение знаний

Этот документ:

4\. Основные архитектурные принципы

4.1 Modularity

Принцип



DevOS строится как система независимых модулей.



FACT



05\_DevOS\_Architecture\_Foundation.md определяет:



Module Boundaries;

Module Contracts;

Dependency Rules.

ANALYSIS



Модульная архитектура позволяет:



добавлять новые возможности;

переиспользовать компоненты;

адаптировать платформу под разные отрасли;

уменьшать влияние изменений.

ENGINEERING DECISION



Каждый модуль DevOS должен:



иметь четкую ответственность;

иметь публичный интерфейс;

скрывать внутреннюю реализацию;

минимизировать зависимости.

Правило



Запрещено создавать функции, которые принадлежат сразу нескольким модулям.



Пример:



Плохо:



CRMService



создает задачи



отправляет уведомления



создает отчеты



Почему плохо:



CRM становится зависимым от всей системы.



Правильно:



CRM Module



создает событие:



CustomerCreated





Tasks Module



реагирует:





CreateTask





Notification Module



реагирует:



SendNotification

4.2 API First

Принцип



Любая значимая возможность DevOS должна иметь API-интерфейс.



FACT



Современные SaaS используют:



REST API;

Webhooks;

Integrations;

SDK.

ANALYSIS



API позволяет:



подключать внешние системы;

создавать интеграции;

развивать SaaS;

разделять frontend и backend.

ENGINEERING DECISION



Любая новая функция должна проектироваться следующим образом:



Domain Logic



&#x20;       ↓



Service Layer



&#x20;       ↓



API Contract



&#x20;       ↓



Frontend / External Integration



Запрещено:



создавать бизнес-логику только внутри UI.



4.3 Domain Driven Design

Принцип



Код должен отражать бизнес-модель.



FACT



Исследование клиентов показало:



разные отрасли используют разные сущности:



клиент;

заявка;

проект;

заказ;

документ;

задача.

ANALYSIS



Если код строится вокруг технических деталей, система становится сложной для развития.



ENGINEERING DECISION



Структура должна отражать бизнес-возможности:



Пример:



modules/



&#x20;   crm/



&#x20;   projects/



&#x20;   tasks/



&#x20;   documents/



&#x20;   automation/



а не:



controllers/



services/



models/





для всей системы сразу.



4.4 Security First

Принцип



Безопасность является частью архитектуры, а не дополнительной функцией.



FACT



B2B SaaS требуют:



authentication;

authorization;

audit;

permissions.

ANALYSIS



DevOS будет работать с бизнес-данными клиентов.



Ошибки безопасности могут привести к:



утечке данных;

потере доверия;

невозможности коммерческого использования.

ENGINEERING DECISION



Каждый модуль обязан учитывать:



permissions;

audit;

tenant isolation;

validation.

4.5 Documentation First

Принцип



Документация является частью разработки.



FACT



DevOS использует AI-assisted development.



ANALYSIS



AI без документации:



создает разные подходы;

нарушает архитектуру;

повторяет существующий код.

ENGINEERING DECISION



Код без документации считается незавершенным.



Обязательные элементы:



README;

API documentation;

ADR при архитектурных изменениях;

changelog.

4.6 Automation First

Принцип



Повторяющиеся процессы должны быть автоматизированы.



FACT



01\_Market\_Research и 02\_Client\_Research показали:



Бизнес покупает автоматизацию:



заявок;

уведомлений;

отчетов;

документов;

интеграций.

ANALYSIS



DevOS сама должна демонстрировать этот принцип.



ENGINEERING DECISION



При проектировании функции необходимо задавать вопрос:



Может ли этот процесс выполняться автоматически?



4.7 Configuration over Hardcoding

Принцип



Настройки должны быть данными, а не кодом.



Пример плохого решения:

if company == "clinic":

&#x20;   send\_patient\_notification()

Правильный подход:

Workflow Configuration



↓



Notification Rule



↓



Execution

ENGINEERING DECISION



Бизнес-правила должны быть максимально конфигурируемыми.



4.8 Reuse over Duplication

Принцип



Каждый новый компонент должен проверять существующие возможности.



Перед созданием:



New Feature



необходимо ответить:



Есть ли уже такой компонент?

Можно ли расширить существующий?

Может ли это стать общим модулем?

ENGINEERING DECISION



Дублирование функциональности запрещено без документированного основания.

5.2 Главный принцип структуры проекта

FACT



05\_DevOS\_Architecture\_Foundation.md определяет:



DevOS является модульной платформой.

Modular Monolith Architecture

6\. Module Development Rules

6.1 Назначение



Этот раздел определяет:



как создавать новые модули DevOS.



FACT



Предыдущие исследования показали:



Главная ценность DevOS:



не количество функций,



а возможность повторного использования.



ANALYSIS



Без правил создания модулей система станет набором несвязанных функций.



ENGINEERING DECISION



Каждый новый модуль проходит обязательную архитектурную проверку.



6.2 Когда создавать новый модуль



Новый модуль создается только если выполняются условия:



Условие 1



Есть отдельная бизнес-ответственность.



Пример:



CRM:



управление клиентами.



Tasks:



управление задачами.



Условие 2



Функциональность потенциально может использоваться несколькими продуктами.



Условие 3



Компонент имеет собственные:



данные;

правила;

процессы.

6.3 Когда НЕ создавать новый модуль



Запрещено создавать модуль для:



одной функции;

одного экрана;

одного клиента;

временного решения.



Плохо:



BirthdayNotificationModule



Лучше:



Notifications Module



\+



Notification Rules

Отвечает за:



бизнес-сущности;

правила;

ограничения.



Не должен зависеть от:



базы данных;

Пример:



Customer

Отвечает за:



сценарии использования.



Например:



CreateCustomer



AssignTask



GenerateReport



Application Layer:



может использовать:



domain;

interfaces.



Но не должен напрямую работать с:



SQL;

внешними API.

6.7 Infrastructure Layer



Отвечает за:



базы данных;

внешние сервисы;

файловое хранилище;

очереди.



Пример:



PostgresCustomerRepository



TelegramNotificationProvider

6.8 API Layer



Отвечает за:



REST endpoints;

validation;

authentication;

DTO.



API слой не содержит бизнес-логику.



Запрещено:



@app.post("/customer")

def create\_customer():



&#x20;   save\_database()



&#x20;   send\_email()



&#x20;   calculate\_discount()



Правильно:



@app.post("/customer")

def create\_customer():



&#x20;   customer\_service.create()

6.9 Module Manifest



Каждый модуль обязан иметь файл:

## 05A_Architecture_Rules.md (Продолжение)

10\. API Rules

Назначение



API является основным контрактом между всеми компонентами DevOS.



Каждый модуль обязан предоставлять стабильный, документированный и обратно совместимый интерфейс.



Архитектурный принцип:



Модули общаются через контракт, а не через внутреннюю реализацию.



10.1 API First

Правило



Любая новая функциональность сначала проектируется как API.



Только после утверждения API начинается реализация.



Почему



Позволяет:



разрабатывать Backend и Frontend независимо;

создавать SDK;

использовать платформу через интеграции;

автоматически генерировать документацию;

избежать несовместимых интерфейсов.

10.2 REST Standards



DevOS придерживается REST как базового стандарта.



Используются только существительные.



Правильно



GET    /users

POST   /users

GET    /users/{id}

PATCH  /users/{id}

DELETE /users/{id}



Неправильно



/createUser

/getUser

/deleteTask

/updateProject

10.3 HTTP Methods

Method	Использование

GET	получение данных

POST	создание

PUT	полная замена

PATCH	частичное изменение

DELETE	удаление (soft delete)

10.4 Versioning



Все публичные API имеют версию.



/api/v1/

/api/v2/



Запрещено



/api/users



без версии.

Валидация производится:

Проверяются:

права доступа.

Практически все зрелые SaaS (Supabase, Appwrite, Directus, HubSpot, Stripe API) используют контрактный подход с OpenAPI и версионированием API.



ANALYSIS



Стандартизированный API снижает стоимость интеграций, упрощает разработку SDK и позволяет безопасно развивать платформу без поломки клиентов.



ENGINEERING DECISION



API DevOS проектируется по принципу API First, использует OpenAPI, DTO, единый формат ошибок и обязательное версионирование.

Проверка безопасности.

Code Review человеком.

FACT



Практики Test Pyramid, рекомендации Martin Fowler и опыт зрелых инженерных команд подтверждают, что сочетание модульных, интеграционных и API-тестов обеспечивает наилучшее соотношение стоимости и надежности.



ANALYSIS



При использовании AI вероятность быстрого появления большого объема кода возрастает. Соответственно, возрастает риск накопления скрытых дефектов без автоматической проверки.



ENGINEERING DECISION



Тестирование становится обязательной частью Definition of Done. Код без необходимых тестов не считается готовым к интеграции.

14\. AI Development Rules

Назначение



DevOS проектируется как AI-Augmented Development Platform.



AI не является архитектором проекта.



AI является исполнителем инженерных решений, зафиксированных в документации.



Любое фундаментальное решение принимает человек.



14.1 Главный принцип



Перед генерацией любого кода AI обязан:



изучить соответствующую документацию;

определить затрагиваемые модули;

проверить архитектурные ограничения;

только после этого приступать к реализации.

14.2 AI запрещено



AI не имеет права самостоятельно:



изменять архитектуру;

изменять модульные границы;

менять структуру БД;

менять API без согласования;

удалять документацию;

нарушать принятые правила;

изменять соглашения именования;

объединять независимые модули;

удалять тесты;

игнорировать существующие сервисы.

14.3 AI обязан



Перед созданием кода AI обязан:



✓ прочитать Architecture Rules



✓ определить используемый модуль



✓ использовать существующие сервисы



✓ соблюдать Naming Convention



✓ соблюдать API Rules



✓ соблюдать Security Rules



✓ написать тесты



✓ обновить документацию



✓ объяснить внесённые изменения



14.4 AI не создаёт новую архитектуру



Если задача требует изменения архитектуры,



AI должен остановиться и сообщить:



Данная задача требует архитектурного решения.



Необходимо создать ADR.



Самостоятельное изменение архитектуры запрещено.



14.5 AI не создаёт дублирование



Перед созданием нового класса,



сервиса,



endpoint,



компонента,



AI обязан проверить,



существует ли уже аналогичная функциональность.



Если существует —



используется существующая реализация.



14.6 AI обязан соблюдать модульность



Нельзя обращаться напрямую:



CRM



↓



Database



↓



Tasks



Разрешено только:



CRM



↓



Public API



↓



Tasks

CHANGELOG

API

README

MODULE\_SPECIFICATION

14.8 AI и тестирование



Любой созданный AI код обязан сопровождаться:



Unit Test;

Integration Test (если применимо);

обновлением существующих тестов при изменении поведения.

14.9 AI и безопасность



AI запрещено:



отключать проверки безопасности;

временно удалять авторизацию;

использовать тестовые секреты;

хранить пароли в коде;

обходить RBAC;

отключать аудит.

14.10 AI и рефакторинг



Рефакторинг допускается только если:



сохраняется публичный контракт;

проходят все тесты;

обновлена документация;

не нарушены архитектурные ограничения.

FACT



Современные AI Coding Assistants способны значительно ускорять разработку, но склонны к локальной оптимизации и не обладают полной архитектурной памятью проекта.



ANALYSIS



Без жёстких правил AI постепенно начинает создавать дублирование, нарушать границы модулей и увеличивать технический долг.



ENGINEERING DECISION



Документация становится главным источником контекста для AI. AI рассматривается как исполнитель, а не как источник архитектурных решений.

руководств по разработке;

CI/CD-процессов;

AI Prompt Library.

Какие архитектурные решения могут измениться



Допускается изменение только тех правил, которые будут опровергнуты:



практическим опытом разработки;

результатами эксплуатации;

новыми исследованиями рынка;

изменением технологического стека.



Изменение возможно только через новый ADR с указанием причин.



Риски отсутствия данного документа



При отсутствии единых Architecture Rules возникают следующие риски:



накопление технического долга;

несовместимые модули;

различия в стиле разработки;

ухудшение качества AI-генерируемого кода;

снижение сопровождаемости платформы;

невозможность масштабирования команды.

20\. Open Questions



На момент утверждения документа остаются вопросы, требующие дополнительного исследования:



Следует ли внедрять Event Sourcing для отдельных модулей или использовать классическую модель хранения данных?

Требуется ли выделение отдельного API Gateway при первых версиях DevOS?

Нужно ли поддерживать GraphQL наряду с REST или отложить это до появления соответствующих требований?

Следует ли использовать модульную монорепозиторию (Monorepo) или перейти к нескольким репозиториям по мере роста платформы?

Какие требования к производительности должны стать обязательными для модулей MVP?

Нужно ли вводить обязательные Architecture Fitness Functions (автоматические архитектурные проверки) уже на этапе MVP?

Какой уровень автоматизированной проверки AI-кода должен быть внедрен до первой коммерческой версии?



Все ответы на данные вопросы должны основываться на практическом опыте и дополнительных исследованиях, а не на предположениях.
