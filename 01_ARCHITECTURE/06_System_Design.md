1\. Executive Summary



Настоящий документ является главным техническим описанием архитектуры DevOS.



Если документ 05\_DevOS\_Architecture\_Foundation.md отвечает на вопрос:



«Какие архитектурные принципы лежат в основе DevOS?»



то данный документ отвечает на следующий уровень:



«Как именно должна быть устроена система, чтобы реализовать эти принципы?»



Это не документация по конкретному коду.



Это техническая спецификация системы.



Именно на основании данного документа AI (Cursor, Claude Code и другие агенты) должны иметь возможность реализовывать новые модули, не нарушая архитектурную целостность платформы.



Главная цель архитектуры DevOS — создать Business Operating System, которая:



масштабируется горизонтально;

расширяется модулями;

поддерживает множество компаний (multi-tenancy);

пригодна для коммерческой разработки;

может развиваться в полноценный SaaS;

сохраняет единую архитектурную модель независимо от количества модулей.

FACT



Исследования современных платформ (Supabase, Appwrite, Directus, Plane, Grafana, Metabase, Appsmith, Budibase и др.), проведенные в документе 04\_SaaS\_Research.md, показывают, что зрелые системы строятся вокруг общей платформы сервисов, а не набора изолированных приложений.



ANALYSIS



Платформенная архитектура уменьшает стоимость разработки новых модулей, снижает дублирование функциональности и повышает скорость вывода новых решений.



ENGINEERING DECISION



DevOS проектируется как Platform First Architecture, где общие сервисы (идентификация, права, события, поиск, уведомления, аудит и интеграции) являются частью платформы и используются всеми бизнес-модулями.

ANALYSIS

ENGINEERING DECISION



Любая новая функциональность сначала проверяется на возможность реализации через существующий платформенный сервис. Создание нового инфраструктурного компонента допускается только при отсутствии возможности повторного использования.



6\. Layered Architecture



DevOS использует многослойную архитектуру (Layered Architecture) с четким разделением ответственности. Это решение основано на выводах из 04\_SaaS\_Research.md и соответствует принципам, закрепленным в 05A\_Architecture\_Rules.md.



Слои системы

Presentation Layer

&#x20;       │

Application Layer

&#x20;       │

Domain Layer

&#x20;       │

Infrastructure Layer

Presentation Layer



Отвечает только за взаимодействие с пользователем и внешними клиентами API.



Включает:



Web UI;

REST Controllers;

WebSocket Endpoints;

API Gateway.



Не содержит:



бизнес-логики;

SQL-запросов;

прямой работы с внешними сервисами.

Application Layer



Оркестрация сценариев использования (Use Cases).



Отвечает за:



координацию сервисов;

управление транзакциями;

проверку прав доступа;

запуск бизнес-процессов.



Не содержит сложных бизнес-правил предметной области.



Domain Layer



Центр бизнес-логики платформы.



Содержит:



Entities;

Value Objects;

Domain Services;

Domain Events;

Business Rules.



Именно этот слой должен оставаться максимально независимым от инфраструктуры.



Infrastructure Layer



Отвечает за реализацию технических деталей.



Примеры:



PostgreSQL;

Redis;

Object Storage;

SMTP;

OAuth Providers;

Message Queue;

Logging.



Этот слой можно заменить без изменения бизнес-логики.



Правило зависимости



Допустимы только следующие направления зависимостей:



Presentation

&#x20;     ↓

Application

&#x20;     ↓

Domain

&#x20;     ↓

Infrastructure



Обратные зависимости запрещены.



FACT



Layered Architecture является отраслевым стандартом для большинства корпоративных платформ и подтверждается архитектурой Directus, Plane, Appwrite, Keycloak и других исследованных решений.



ANALYSIS



Разделение ответственности снижает связанность системы, облегчает тестирование и позволяет AI безопасно изменять отдельные части кода без нарушения общей архитектуры.



ENGINEERING DECISION



Все компоненты DevOS обязаны соответствовать четырехслойной архитектуре. Любое отклонение требует отдельного Architecture Decision Record (ADR).



7\. Backend Architecture



Backend DevOS проектируется как модульное монолитное приложение (Modular Monolith) с возможностью последующей эволюции отдельных компонентов в самостоятельные сервисы при наличии подтвержденной необходимости.



Такой подход выбран на основании исследований зрелых Open Source платформ и рекомендаций, сформированных в предыдущих документах.



7\. Backend Architecture

Цель Backend



Backend DevOS является центральным уровнем исполнения всей платформы.



Его задача — не просто обслуживать HTTP-запросы, а обеспечивать единый механизм выполнения бизнес-процессов независимо от того, какой модуль используется: CRM, Projects, Documents, Automation или любой будущий модуль.



Главная цель архитектуры Backend — обеспечить:



слабую связанность компонентов;

независимое развитие модулей;

повторное использование платформенных сервисов;

возможность безопасного расширения AI-агентами;

масштабирование без архитектурной деградации.

Архитектурный стиль



На основании исследований (04\_SaaS\_Research.md) и архитектурных ограничений (05\_DevOS\_Architecture\_Foundation.md) для DevOS принимается следующая стратегия.



Базовый стиль



Modular Monolith



Причины выбора:



проще сопровождать;

проще тестировать;

отсутствуют проблемы распределённых транзакций;

проще развивать небольшой командой;

лучше подходит для AI-разработки;

подтвержден зрелыми Open Source платформами.

Возможность эволюции



Архитектура должна позволять при необходимости выделить отдельные сервисы.



Например:



CRM

Это достигается за счет:

отсутствия прямых зависимостей;

событийной модели;

API между модулями.

FACT

ANALYSIS



Фоновые задания уменьшают время ответа API, улучшают пользовательский опыт и позволяют безопасно масштабировать ресурсоемкие процессы независимо от обработки интерактивных запросов.



ENGINEERING DECISION



Все операции, выполнение которых потенциально превышает целевое время ответа API или зависит от внешних сервисов, должны реализовываться через очередь фоновых задач с механизмами повторных попыток, журналирования и мониторинга.



8\. Frontend Architecture

Назначение Frontend



Frontend DevOS является универсальным клиентом платформы.



Он не должен содержать бизнес-логику.



Его задача:



отображение данных;

взаимодействие с пользователем;

маршрутизация;

управление состоянием интерфейса;

выполнение команд пользователя.

Основные принципы



Frontend строится по принципам:



Component First;

Feature Based;

API First;

Design System Driven;

Reusable UI;

Responsive by Default;

Accessibility by Default.

Архитектурные уровни

Application



↓



Pages



↓



Features



↓



Widgets



↓



Shared UI



↓



Core Components

Application



Отвечает за:



инициализацию;

роутинг;

авторизацию;

глобальную конфигурацию;

Страницы являются контейнерами.



Например



Dashboard



CRM



Projects



Reports

Users



Страница объединяет функциональность, но не реализует её.

Feature — законченный пользовательский сценарий.



Например



Create Customer



Assign Task



Upload File



Export Report



Approve Invoice



Feature может использовать компоненты нескольких модулей, оставаясь самостоятельной единицей.



Widgets



Независимые блоки интерфейса.



Например



Activity Feed



Statistics Card



Task List



Customer Summary



Calendar



Recent Documents



Любой Widget должен быть пригоден для повторного использования.



Shared UI



Содержит переиспользуемые элементы.



Например



Buttons



Inputs



Dialogs



Tables



Forms



Tabs



Dropdowns



Badges



Cards



Icons



Запрещается создавать локальные версии компонентов при наличии общего аналога.



Управление состоянием



Состояние разделяется на несколько уровней:



серверное состояние;

состояние интерфейса;

состояние формы;

локальное состояние компонента.



Каждый тип состояния управляется независимо. Это предотвращает избыточную связанность и упрощает сопровождение.



Работа с API



Frontend взаимодействует только с публичными API платформы.



Запрещено:



обращаться напрямую к базе данных;

формировать SQL-запросы;

обходить слой авторизации.



Все сетевые вызовы проходят через единый API Client с централизованной обработкой:



аутентификации;

обновления токенов;

ошибок;

повторных запросов;

журналирования клиентских ошибок.

Навигация



Навигация должна быть модульной.



Подключение нового модуля должно автоматически регистрировать:



маршруты;

пункты меню;

права доступа;

локализацию;

иконки и метаданные.



Это позволит расширять платформу без изменения существующих модулей.



FACT



Практически все исследованные SaaS-платформы используют компонентный UI, централизованную дизайн-систему и единый механизм работы с API.



ANALYSIS



Единый подход к компонентам и взаимодействию с API обеспечивает консистентный пользовательский опыт, ускоряет разработку и снижает вероятность появления дублирующихся решений.



ENGINEERING DECISION



Frontend DevOS реализуется как модульное приложение с единой дизайн-системой, общей библиотекой компонентов и стандартизированным API-клиентом. Ни один модуль не должен самостоятельно реализовывать собственную систему сетевого взаимодействия или базовые UI-компоненты.



9\. Data Architecture

Назначение



Data Architecture определяет принципы хранения информации в DevOS.



Цель архитектуры хранения данных — обеспечить:



единое представление данных;

независимость модулей;

масштабируемость;

возможность безопасного расширения;

поддержку multi-tenancy;

возможность аналитики без нарушения бизнес-логики.



Архитектура данных должна оставаться стабильной независимо от количества модулей платформы.



Основные принципы

11\. API Architecture

Основная концепция



Одним из наиболее устойчивых выводов исследования SaaS (04\_SaaS\_Research.md) стало широкое распространение подхода API First.



Следовательно, API рассматривается не как вспомогательный слой, а как основной контракт платформы.



Любой пользовательский интерфейс, мобильное приложение, интеграция или AI-агент должны взаимодействовать с платформой одинаковым способом — через публичный API.



Основные принципы



API должно быть:



стабильным;

документированным;

версионируемым;

предсказуемым;

независимым от внутренней реализации модулей.

Архитектурная схема

Client



↓



REST API



↓



Application Services



↓



Domain



↓



Repository

Контракт API



Каждый публичный метод обязан иметь:



описание;

DTO запроса;

DTO ответа;

коды ошибок;

требования авторизации;

примеры использования.

Версионирование



Публичный API должен поддерживать явное версионирование.



Например:



/api/v1/



Изменения, нарушающие обратную совместимость, допускаются только в новой версии API.



DTO



Передача данных осуществляется только через DTO.



Запрещено возвращать внутренние доменные объекты напрямую.



Это обеспечивает независимость API от внутренней модели данных.



Валидация



Проверка данных выполняется до передачи запроса в Application Layer.



Проверяются:



обязательные поля;

форматы;

диапазоны значений;

ограничения длины;

бизнес-предусловия первого уровня.

Идемпотентность



Операции создания и обновления, где это возможно, должны поддерживать идемпотентность для безопасного повторного выполнения запросов внешними системами.



API для модулей



Каждый модуль публикует только свои публичные контракты.



Внутренние сервисы не могут использоваться другими модулями напрямую.



FACT



API First является повторяющимся архитектурным паттерном среди исследованных SaaS-платформ и Open Source решений.



ANALYSIS



Единый контракт API снижает связанность между компонентами, облегчает разработку интеграций и позволяет использовать один и тот же Backend для Web, Mobile и AI-клиентов.



ENGINEERING DECISION



API становится обязательной публичной границей каждого модуля DevOS. Любое внешнее взаимодействие осуществляется через документированные версии API.



12\. Authentication \& Authorization

Общая стратегия



Система безопасности строится по принципу Security First, принятому в 05A\_Architecture\_Rules.md и подтвержденному анализом Keycloak, Appwrite, Supabase, Directus и других платформ.



Аутентификация и авторизация рассматриваются как платформенные сервисы и не реализуются повторно в отдельных модулях.



Authentication



Платформа отвечает за подтверждение личности пользователя.



Поддерживаемые механизмы определяются отдельно, но архитектура должна предусматривать возможность подключения нескольких провайдеров аутентификации без изменения бизнес-модулей.



Authorization



После подтверждения личности выполняется проверка прав доступа.



Авторизация строится вокруг следующих сущностей:



User;

Organization;

Role;

Permission;

Resource;

Action.

RBAC



Базовой моделью управления доступом является Role-Based Access Control.



Права назначаются ролям, роли — пользователям.



Модули определяют собственные разрешения, но используют единый платформенный механизм проверки.



Проверка доступа



Каждая операция проходит последовательные этапы:



Authentication

&#x20;       ↓

Organization Context

&#x20;       ↓

Role Resolution

&#x20;       ↓

Permission Check

&#x20;       ↓

Business Rule Validation



Это разделяет техническую авторизацию и бизнес-ограничения.



Принцип минимальных привилегий



По умолчанию пользователю не предоставляется доступ ни к одной операции, пока он явно не назначен через роль или разрешение.



Аудит безопасности



Все значимые события безопасности журналируются:



вход;

выход;

смена пароля;

изменение ролей;

отказ в доступе;

использование API-токенов.

Подготовка к расширению



Архитектура должна позволять в будущем добавить:



Attribute-Based Access Control (ABAC);

политики доступа;

делегирование полномочий;

временные роли;

сервисные учетные записи.



Эти возможности не являются обязательными для MVP, но учитываются при проектировании платформенного слоя.



FACT



Исследованные корпоративные платформы используют централизованные сервисы аутентификации и авторизации, исключая повторную реализацию механизмов безопасности внутри бизнес-модулей.



ANALYSIS



Централизация безопасности обеспечивает единое поведение системы, уменьшает вероятность ошибок реализации и упрощает сопровождение при росте количества модулей.



ENGINEERING DECISION



Identity, Authentication, Authorization и RBAC являются обязательными платформенными сервисами DevOS. Ни один бизнес-модуль не реализует собственную систему управления пользователями или правами доступа.



13\. Event Architecture

Назначение



По мере роста платформы количество взаимодействий между модулями будет постоянно увеличиваться.



Если каждый модуль будет напрямую вызывать другой, система быстро превратится в tightly coupled architecture.



Поэтому DevOS использует событийную модель как один из основных способов взаимодействия между модулями.



Важно отметить:



Это не означает, что вся архитектура строится на Event Sourcing.



Исследование SaaS (04\_SaaS\_Research.md) не подтвердило необходимость использования Event Sourcing как базовой архитектуры для MVP.



Поэтому принимается более практичный подход:



синхронные операции — через API;

асинхронные процессы — через Domain Events.

Основные принципы



Событие представляет собой факт, который уже произошел.



Например



CustomerCreated



а не



CreateCustomer



или



NeedCreateCustomer



События описывают прошлое.



Команды описывают намерение.



Это принципиально разные вещи.



Когда использовать события



Используются если необходимо:



уведомить другие модули;



запустить автоматизацию;



обновить аналитику;



выполнить фоновые процессы;



запустить интеграции;



отправить email;



отправить Telegram;



обновить Dashboard.



Не используются:



для обычного CRUD;



для получения данных;



для чтения информации;



для простых запросов.



Пример



Создание клиента



CRM



↓



Create Customer



↓



Save Customer



↓



Publish CustomerCreated



После этого независимо запускаются



Audit

↓



Automation



↓



Analytics



↓



Webhook



↓



Search Index



CRM ничего не знает о них.

Идемпотентность



Каждый обработчик обязан корректно переживать повторную обработку события.



Причина:



повторная доставка;



ошибки сети;

Версионирование событий



Публичные события являются контрактом.

Допускается:

FACT

ANALYSIS



События позволяют добавлять новые возможности без изменения существующих модулей.



ENGINEERING DECISION



Все межмодульные процессы, не требующие мгновенного ответа пользователю, реализуются через Event Bus и Domain Events.

Практически все зрелые платформы используют отдельный сервис хранения файлов с разделением бинарных данных и метаданных.

Разделение хранения упрощает масштабирование, резервное копирование и замену инфраструктуры.



ENGINEERING DECISION



File Storage реализуется как платформенный сервис с единым API и абстракцией Storage Provider.



16\. Caching Strategy

Назначение



Кэширование рассматривается как инфраструктурный механизм повышения производительности.



Использование кэша не должно изменять бизнес-логику.



Что допускается кэшировать



Справочники;



настройки;



RBAC;



конфигурацию;



результаты поиска;



агрегированные отчеты;



данные Dashboard.



Что запрещено кэшировать без отдельного обоснования



критические финансовые операции;



данные, требующие строгой консистентности;



права доступа без механизма инвалидирования.



Инвалидация



Любое изменение данных должно приводить к предсказуемому обновлению или очистке кэша.



FACT



Практически все исследованные SaaS используют централизованное кэширование конфигурации, метаданных и аналитических данных.



ANALYSIS



Кэш эффективен только при наличии четкой стратегии инвалидирования. Иначе он становится источником труднообнаружимых ошибок.



ENGINEERING DECISION



Кэширование в DevOS рассматривается как оптимизация производительности, а не как источник истины. Источником истины всегда остается основное хранилище данных.

Очереди позволяют изолировать ресурсоемкие процессы от интерактивной работы пользователей и значительно повышают устойчивость системы.



ENGINEERING DECISION



Все операции, потенциально влияющие на производительность пользовательского интерфейса, должны выполняться через централизованный сервис очередей.

20\. Стратегия обработки ошибок (Error Handling Strategy)

Назначение



Обработка ошибок должна быть единообразной во всех модулях DevOS. Ошибки являются частью публичного контракта системы и должны быть предсказуемыми как для пользователей, так и для интеграций.



Основные цели:



единый формат ошибок;

удобная диагностика;

безопасное отображение информации;

трассировка всех исключений;

минимизация потери контекста.

Принципы

Ошибка — часть API



Каждый endpoint обязан возвращать предсказуемый ответ.



Даже при возникновении исключения структура ответа остается одинаковой.



Пример:



{

&#x20; "success": false,

&#x20; "error": {

&#x20;   "code": "TASK\_NOT\_FOUND",

&#x20;   "message": "Task not found",

&#x20;   "details": null,

&#x20;   "traceId": "01HJ..."

&#x20; }

}

Пользовательские ошибки



Возникают при неправильных действиях пользователя.



Например:



неверный пароль;

отсутствует обязательное поле;

нарушение бизнес-правила;

отсутствие доступа.



Такие ошибки:



понятны пользователю;

не содержат технических деталей;

не логируются как Critical.

Системные ошибки



Возникают внутри платформы.



Например:



недоступна БД;

ошибка очереди;

ошибка файлового хранилища;

переполнение памяти.



Такие ошибки:



логируются полностью;

имеют Trace ID;

доступны администраторам.

Необработанных исключений быть не должно



Любое исключение проходит через Global Exception Handler.



Запрещается:



return str(exception)



или



print(exception)

Категория	HTTP	Пример

Validation	400	неверные данные

Authentication	401	требуется вход

Authorization	403	нет прав

Not Found	404	объект отсутствует

Business Rule	422	нарушение правил

Rate Limit	429	превышен лимит

Internal	500	ошибка сервера

Все:

Worker



используют один Trace ID.



Это позволяет восстановить полную цепочку обработки.

↓

↓

↓

↓



Audit

Например:

business rule

После нескольких неудачных попыток задача переносится в DLQ.



Причины:

поврежденный payload

Практически все зрелые SaaS (Stripe, GitHub, Supabase, Atlassian) используют единые форматы ошибок и механизм Correlation/Trace ID.

Без унифицированной обработки ошибок система быстро становится трудно поддерживаемой.



ENGINEERING DECISION



DevOS использует глобальную стратегию обработки ошибок с единым Error Contract, Trace ID и централизованным Exception Handler.

24\. Архитектура развертывания (Deployment Architecture)

Назначение



Архитектура развертывания определяет, каким образом DevOS будет развертываться в различных сценариях эксплуатации без изменения прикладной архитектуры.



Документ не фиксирует конкретного облачного провайдера или поставщика инфраструктуры. Он определяет архитектурные принципы, которым должна соответствовать любая реализация.



Поддерживаемые модели развертывания



DevOS должна поддерживать несколько сценариев эксплуатации.



1\. Single Server



Используется:



разработка;

локальная установка;

небольшие компании;

демонстрационные среды.

Backend

Frontend

Database

Queue

Storage

Преимущества:



минимальная стоимость;

простота обслуживания.



Ограничения:



ограниченная масштабируемость;

единая точка отказа.

2\. Self-hosted Enterprise



Предназначен для компаний, разворачивающих систему внутри собственной инфраструктуры.



Особенности:



отдельные серверы приложений;

собственная БД;

внутренние интеграции;

корпоративная авторизация;

внутренние сети.



Используется при повышенных требованиях к безопасности.



3\. Cloud SaaS



Архитектура должна поддерживать полноценную SaaS-модель.



Особенности:



множество арендаторов;

автоматическое масштабирование;

централизованное управление;

отказоустойчивость;

автоматическое резервное копирование.

Часть компонентов располагается локально.



Часть — в облаке.



Например:

↓

↓



Cloud Notifications



↓

↓



Cloud Backup

Контейнеризация



Все основные компоненты должны поддерживать контейнеризацию.



Контейнер рассматривается как стандартный способ упаковки приложения.



Каждый сервис разворачивается независимо.

балансировку нагрузки.

Конфигурация



Конфигурация полностью отделяется от кода.

Например:

Архитектура должна предусматривать:



резервные копии БД;

резервные копии файлов;

резервные копии конфигурации;

проверку восстановления.



Наличие резервной копии без проверки восстановления не считается выполнением требования.

ANALYSIS



Поддержка нескольких моделей развертывания позволит использовать одну архитектурную базу как для коммерческих внедрений, так и для будущей SaaS-версии DevOS.



ENGINEERING DECISION



Deployment Architecture должна оставаться инфраструктурно-независимой. Выбор конкретных инструментов (Docker Compose, Kubernetes и др.) фиксируется на этапе реализации, а не в архитектурной спецификации.



25\. Технологические ограничения (Technology Constraints)

Назначение



Этот раздел определяет ограничения, которые защищают архитектуру DevOS от технологической деградации.



Ограничения важнее выбора конкретных библиотек.



Ограничение №1



Архитектура не должна зависеть от одного поставщика инфраструктуры.



Причина:



Vendor Lock-in значительно усложняет развитие платформы.



Ограничение №2



Бизнес-логика не должна зависеть от UI.



Любой модуль должен иметь возможность работать:



через Web UI;

через API;

через CLI (при необходимости);

через автоматизацию.

Ограничение №3



API — обязательный публичный контракт.



Изменение API требует:



анализа обратной совместимости;

обновления документации;

фиксации в Decision Log.

Ограничение №4



Никаких циклических зависимостей между модулями.



Любая зависимость должна быть направленной.



Ограничение №5



Все изменения модели данных выполняются только через миграции.



Прямое изменение структуры базы данных запрещено.



Ограничение №6



Внешние интеграции должны быть изолированы.



Ни один модуль не должен зависеть напрямую от стороннего API.



Используются адаптеры или Integration Layer.



Ограничение №7



Любая длительная операция должна иметь возможность выполнения асинхронно.



Ограничение №8



Все действия пользователя должны быть трассируемыми.



Если действие невозможно отследить, архитектура считается неполной.



Ограничение №9



Все конфигурационные параметры должны изменяться без перекомпиляции приложения.



Ограничение №10



Каждый новый модуль обязан соответствовать требованиям:



Multi-tenancy;

RBAC;

Audit;

API;

Logging;

Documentation.

FACT



Ограничения такого типа соответствуют практикам зрелых платформ и предотвращают накопление технического долга.



ANALYSIS



Явно зафиксированные архитектурные ограничения позволяют AI-ассистентам генерировать код без нарушения базовых принципов системы.



ENGINEERING DECISION



Technology Constraints являются обязательными архитектурными инвариантами и не могут быть изменены без оформления Architecture Decision Record (ADR).
