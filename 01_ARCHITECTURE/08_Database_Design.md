\# 1. Executive Summary



Настоящий документ определяет архитектуру хранения данных платформы DevOS.



Он является единым источником истины для проектирования:



\- структуры базы данных;

\- моделей ORM;

\- миграций;

\- индексов;

\- ограничений;

\- связей между сущностями;

\- стратегии масштабирования;

\- стратегии хранения истории изменений.



Документ не описывает бизнес-логику модулей. Его задача — определить правила хранения данных таким образом, чтобы архитектура оставалась масштабируемой, расширяемой и независимой от конкретной технологии реализации.



Основной принцип DevOS:



> Каждая Business Capability владеет собственными данными.



Никакой модуль не имеет права напрямую изменять данные другого модуля.



Все взаимодействие выполняется через публичные API или события.

\# 4. Database Design Principles



Все проектирование базы данных DevOS подчиняется единым принципам.



\---



\## Principle 1



\### Business Capability Ownership



Каждая таблица принадлежит одному модулю.



Пример



CRM



владеет



Customer



Deal



Company



Contact



Projects



владеет



Project



Milestone



Board



Identity



владеет



User



Credential



Session



Никакая таблица не может одновременно принадлежать двум модулям.



\---



\## Principle 2



\### Single Source of Truth



Каждая бизнес-сущность существует только в одном месте.



Например



Информация о пользователе хранится только в Identity.



CRM хранит только ссылку.



Projects хранит только ссылку.



Documents хранит только ссылку.



Запрещается дублировать данные.



\---



\## Principle 3



\### Explicit Relationships



Все связи должны быть явными.



Используются:



Foreign Keys



Unique Constraints



Indexes



Check Constraints



Не допускаются скрытые зависимости.



\---



\## Principle 4



\### Immutable History



История изменений не должна уничтожаться.



Используются:



Audit



Versioning



Soft Delete



Event History



\---



\## Principle 5



\### Configuration over Hardcoding



Изменяемые параметры не должны храниться в коде.



Используются:



Configuration Tables



Reference Tables



Lookup Tables



\---



\## Principle 6



\### Modular Database



Модуль владеет своими таблицами.



Другие модули используют API.



Не допускается прямое изменение таблиц другого модуля.

\# 8. Multi-Tenant Data Model



\## Overview



DevOS проектируется как платформа, способная работать как:



\- Single Organization System;

\- Multi-Organization Platform;

\- Commercial SaaS.



Поэтому модель хранения данных изначально должна учитывать изоляцию данных различных организаций.



Основная иерархия выглядит следующим образом:



Platform

│

├── Organization

│   ├── Workspace

│   │   ├── Users

│   │   ├── Business Modules

│   │   ├── Projects

│   │   ├── CRM

│   │   ├── Documents

│   │   └── Settings

│   │

│   └── Shared Resources

│

└── Platform Services



Каждая бизнес-сущность принадлежит определенной организации.



Все запросы к данным обязаны учитывать контекст текущей организации.



\---



\## Tenant Isolation



Каждая запись бизнес-данных содержит ссылку:

Например:

Project



id



organization\_id



name



status



Invoice



id

number



amount



Это обеспечивает логическую изоляцию данных.



\---



\## Workspace Strategy



Организация может содержать несколько рабочих пространств.



Например:

↓

CRM



Projects



Tasks



↓



Workspace C



CRM



Projects

Workspace является уровнем логического разделения внутри организации.



\---



\## Shared Platform Tables



Некоторые таблицы являются глобальными и не принадлежат конкретной организации.



Например:



Countries



Currencies



Languages



Timezones



System Settings



Feature Flags



Module Registry



Эти таблицы доступны только для чтения.



\---



\## Engineering Decision



Используется стратегия Shared Database + Tenant Identifier.



Причины:



\- проще сопровождать;

\- дешевле эксплуатация;

\- проще резервное копирование;

\- подходит для большинства коммерческих проектов;

\- легко масштабируется до десятков тысяч организаций.



Переход к Database-per-Tenant возможен в будущем без изменения бизнес-логики.

\# 9. Primary Key Strategy



\## Identifier Requirements



Каждая сущность DevOS должна иметь:



\- глобально уникальный идентификатор;

\- невозможность конфликтов;

\- совместимость с распределенной архитектурой;

\- независимость от конкретной базы данных.



\---



\## Identifier Type



Основной тип идентификатора:



UUID v7 (при поддержке)



или



ULID



Причины выбора:



\- сортировка по времени;

\- высокая производительность индексов;

\- отсутствие конфликтов;

\- удобство распределенной генерации.



Автоинкрементные числовые идентификаторы не используются.



\---



\## Naming Standard

\# 12. Soft Delete Strategy



Удаление записей выполняется логически.



Используется поле:



deleted\_at



Запись считается удаленной, если поле заполнено.



Физическое удаление допускается только:



\- для временных данных;

\- после завершения периода хранения;

\- через фоновые задачи.



\---



\## Преимущества



\- восстановление данных;

\- аудит;

\- соответствие требованиям безопасности;

\- предотвращение случайной потери информации.



\---



\# 13. Audit Strategy



Все изменения критически важных сущностей должны фиксироваться.



Минимально сохраняются:



\- кто изменил;

\- когда изменил;

\- что изменилось;

\- старое значение;

\- новое значение.



\---



Audit Record



id



entity\_type



entity\_id



action



user\_id



timestamp



old\_value



new\_value



\---



Поддерживаемые действия:



CREATE



UPDATE



DELETE



RESTORE



LOGIN



EXPORT



IMPORT



\---



\## Engineering Decision



Audit является обязательной частью платформы.



Ни один Business Module не освобождается от ведения журнала изменений.



\---



\# 14. Versioning Strategy



Для важных сущностей используется оптимистическая блокировка.



Каждая запись содержит поле:



version



При каждом обновлении значение увеличивается.



Это позволяет:



\- предотвращать конфликты;

\- обнаруживать одновременное редактирование;

\- реализовывать безопасное сохранение изменений.



История версий документов может храниться отдельно, если модуль этого требует (например, Documents или Knowledge Base).



\# 15. Index Strategy



\## Purpose



Индексы являются обязательной частью проектирования каждой сущности.



Индекс создается одновременно с проектированием таблицы, а не после появления проблем с производительностью.



\---



\## Primary Index



Каждая таблица имеет:



PRIMARY KEY (id)



\---



\## Foreign Key Indexes



Все внешние ключи индексируются.



Пример:



organization\_id



user\_id



project\_id



customer\_id



role\_id



parent\_id



\---



\## Composite Indexes



Используются для наиболее частых сценариев поиска.



Например:



Customer



(organization\_id, status)



Project



(organization\_id, status)



Task



(project\_id, status)



Document



(organization\_id, category)



\---



\## Unique Indexes



Используются только там, где это действительно необходимо.



Примеры:



email



username



organization\_slug



module\_code



api\_key



\---



\## Search Indexes



Для полнотекстового поиска используются специализированные индексы PostgreSQL.



Поддерживаются:



\- Full Text Search

\- GIN

\- Trigram Indexes (при необходимости)



\---



\## Engineering Decision



Каждый новый модуль обязан документировать:



\- Primary Key

\- Foreign Keys

\- Required Indexes

\- Unique Constraints



до начала реализации.

\# 16. Constraint Strategy



\## Purpose



Все ограничения должны контролироваться на уровне базы данных.



Недостаточно проверять данные только в приложении.



\---



\## Required Constraints



NOT NULL



для обязательных полей.



CHECK



для допустимых диапазонов значений.



UNIQUE



для уникальных бизнес-идентификаторов.



FOREIGN KEY



для обеспечения ссылочной целостности.



\---



\## Example



Invoice



amount > 0



Customer



email unique



Task



status in



Draft



Open



In Progress



Completed



Archived



\---



\## Engineering Decision



Если ограничение можно реализовать средствами PostgreSQL — оно должно быть реализовано именно там.

\# 17. Data Integrity Rules



Основные правила целостности данных.



\---



\## Rule 1



Запрещены "висячие" ссылки.



Каждый внешний ключ обязан ссылаться на существующую запись.



\---



\## Rule 2



Запрещено удаление родительской записи, если существуют зависимые данные.



Используются:



RESTRICT



или



SET NULL



в зависимости от сценария.



\---



\## Rule 3



Все бизнес-операции должны быть транзакционными.



Если операция затрагивает несколько сущностей, изменения фиксируются только после успешного выполнения всех шагов.



\---



\## Rule 4



Запрещено хранение вычисляемых данных без необходимости.



Например:



Полное имя пользователя формируется из имени и фамилии, а не хранится отдельно.



\---



\## Rule 5



Каждая сущность имеет владельца.



Например:



Organization



или



Platform.



Без владельца сущность существовать не может.



\---

\## Engineering Decision

\# 19. JSONB Usage Rules



DevOS использует PostgreSQL JSONB только в строго определенных случаях.



\---



\## Разрешено



\- пользовательские настройки;

\- дополнительные параметры;

\- расширения модулей;

\- конфигурация интеграций;

\- временные данные.



\---



\## Запрещено



Хранить в JSONB:



\- основные бизнес-сущности;

\- связи между сущностями;

\- критически важные данные;

\- данные, участвующие в фильтрации и аналитике.



\---



\## Example



Правильно:



metadata



preferences



custom\_fields



Неправильно:



customer



invoice



project



task



\---



\## Engineering Decision



JSONB рассматривается как механизм расширения модели данных, а не ее основа.

\# 22. Archive Strategy



Архивирование предназначено для уменьшения объема рабочих данных без их удаления.



\---



\## Archive Conditions



Данные могут быть архивированы если:



\- завершены;

\- не изменялись длительное время;

\- не участвуют в активных процессах.



\---



\## Archive Requirements



Архивированные записи:



\- сохраняются;

\- доступны только при специальных запросах;

\- не участвуют в стандартных выборках.



\---



\# 23. Backup \& Recovery Requirements



\## Backup Strategy



Поддерживаются:



\- ежедневные полные резервные копии;

\- инкрементальные копии;

\- журнал транзакций.



\---



\## Recovery Objectives



RPO (Recovery Point Objective)



не более 15 минут.



RTO (Recovery Time Objective)



не более 1 часа.



\---



\## Restore Validation



Каждая резервная копия должна регулярно проверяться путем тестового восстановления.



\---



\## Engineering Decision



Наличие резервной копии без проверки восстановления считается недостаточным уровнем надежности.

\# 24. Database Security Principles



\## Purpose



Безопасность базы данных является частью архитектуры платформы и должна учитываться на этапе проектирования, а не после начала разработки.



\---



\## Principle 1 — Least Privilege



Каждый сервис получает только те права, которые необходимы для его работы.



Запрещается использование учетных записей с расширенными привилегиями для повседневной работы приложения.



\---



\## Principle 2 — Separation of Responsibilities



Права разделяются между различными ролями:



\- Application

\- Migration

\- Administrator

\- Read Only

\- Backup



Каждая роль имеет строго ограниченный набор разрешений.



\---



\## Principle 3 — Sensitive Data Protection



Следующие данные считаются чувствительными:



\- пароли;

\- refresh tokens;

\- API Keys;

\- OAuth Tokens;

\- секреты интеграций;

\- персональные данные (PII).



Для их хранения используются:



\- надежные алгоритмы хеширования;

\- шифрование;

\- безопасное хранение секретов вне репозитория.



\---



\## Principle 4 — Auditability



Все административные действия должны фиксироваться:



\- создание пользователей;

\- изменение ролей;

\- изменение конфигурации;

\- импорт данных;

\- экспорт данных;

\- удаление данных.



\---



\## Principle 5 — Data Isolation



Ни один пользователь не может получить доступ к данным другой организации.



Все запросы проходят обязательную проверку контекста:



Organization → User → Role → Permission → Resource



\---



\## Engineering Decision



Безопасность рассматривается как обязательное архитектурное требование, а не дополнительная функция платформы.



\---



\# 25. Migration Strategy



\## Purpose



Все изменения структуры базы данных выполняются только через систему миграций.



Ручное изменение структуры базы данных запрещено.



\---



\## Migration Principles



Каждая миграция должна:



\- быть атомарной;

\- иметь уникальный идентификатор;

\- быть воспроизводимой;

\- храниться в системе контроля версий;

\- проходить тестирование.



\---



\## Migration Lifecycle



1\. Создание миграции.

2\. Проверка на локальной среде.

3\. Выполнение автоматических тестов.

4\. Применение в тестовой среде.

5\. Применение в production.



\---



\## Rollback



По возможности каждая миграция должна поддерживать откат.



Если откат невозможен, это должно быть явно указано в документации.



\---



\## Seed Data



Начальные данные разделяются на две категории:



\### System Seed



Создаются автоматически:



\- роли;

\- базовые разрешения;

\- языки;

\- валюты;

\- часовые пояса.



\### Demo Seed



Используются только для разработки и тестирования.



Не допускаются в production.



\---



\## Engineering Decision



Структура базы данных считается частью исходного кода и развивается по тем же правилам, что и программный код.



\---



\# 26. Scalability Strategy



\## Purpose



Архитектура хранения данных должна поддерживать рост платформы без фундаментальной переработки модели.



\---



\## Horizontal Scalability



Предусматривается возможность:



\- масштабирования сервисов;

\- разделения нагрузки;

\- использования реплик для чтения;

\- фоновой обработки.



\---



\## Vertical Scalability



Допускается увеличение вычислительных ресурсов без изменения структуры данных.



\---



\## Future Evolution



Архитектура должна допускать:



\- шардирование;

\- выделение отдельных сервисов;

\- независимые базы данных модулей;

\- выделенные поисковые индексы;

\- отдельные аналитические хранилища.



При этом публичные контракты модулей остаются неизменными.



\---



\## Engineering Decision



Модель данных проектируется с учетом долгосрочного развития платформы, но преждевременное усложнение архитектуры не допускается.



\---
