**Status:** Draft

\# Purpose



Documentation Standards определяет единые правила создания, оформления, обновления и сопровождения всей документации проекта DevOS.



Настоящий документ является обязательным как для инженеров проекта, так и для AI-систем, участвующих в разработке.



Его цель — обеспечить единообразие документации независимо от автора, времени создания или области проекта.



Стандарты распространяются на все категории документации DevOS:



\- Research;

\- Architecture;

\- Product;

\- Development;

\- Project;

\- AI Bootstrap.



\---



\# 1. Documentation Philosophy



\## Documentation Is Part of the Architecture



Документация рассматривается как полноценная часть архитектуры DevOS.



Она не является вспомогательным материалом и не создаётся после завершения разработки.



Архитектура, код и документация представляют собой единую инженерную систему.



\---



\## Documentation Before Implementation



Все значимые инженерные решения сначала фиксируются в документации.



После согласования они переходят в реализацию.



Изменение архитектуры без обновления документации считается нарушением инженерного процесса.



\---



\## Single Source of Truth



Каждая инженерная тема должна иметь один официальный документ-владелец.



Например:



\- API — `09\_API\_Design.md`

\- База данных — `08\_Database\_Design.md`

\- Безопасность — `11\_Security\_Model.md`



Дублирование информации между документами не допускается.



\---



\## Long-Term Maintainability



Документация создаётся с расчётом на многолетнее сопровождение проекта.



Предпочтение отдаётся понятным и устойчивым структурам, а не краткосрочным решениям.



\---



\## AI-Oriented Documentation



Документация должна быть одинаково удобной:



\- для инженеров;

\- для AI-систем.



Каждый документ должен легко читаться, иметь предсказуемую структуру и содержать только одну основную область ответственности.



\---



\# 2. Standard Document Structure



Все официальные документы DevOS используют единую базовую структуру.



```

Metadata



↓



Purpose



↓



Main Sections



↓



Engineering Principles



↓



Related Documents



↓



Final Statement

```



Допускается изменение структуры только в случае, если специфика документа требует иной организации материала.



Однако обязательные элементы должны сохраняться.



\---



\## Metadata



Каждый документ начинается с блока метаданных.



Он позволяет быстро определить статус документа и его назначение.



\---



\## Purpose



После метаданных всегда располагается раздел Purpose.



Он отвечает на вопросы:



\- зачем существует документ;

\- какую проблему он решает;

\- за что отвечает;

\- за что не отвечает.



\---



\## Main Content



Основная часть документа содержит профильную информацию.



Именно здесь располагается архитектура, описание продукта, правила или процессы.



\---



\## Engineering Principles



Если документ содержит инженерные рекомендации, он должен завершаться перечнем основных принципов.



Это позволяет быстро понять ключевые ограничения и требования.



\---



\## Related Documents



Документ должен содержать ссылки только на действительно связанные материалы.



Не допускается перечисление всех документов проекта без необходимости.



\---



\## Final Statement



Последний раздел кратко формулирует назначение документа и его место в общей системе документации DevOS.



\---



\# 3. Metadata Standard



Каждый официальный документ обязан содержать единый набор метаданных.



\## Required Fields



Обязательные поля:



\- Status

\- Version

\- Category



\---



\## Recommended Fields



При необходимости могут использоваться:



\- Purpose

\- Related Documents

\- Owner

\- Last Updated



\---



\## Metadata Rules



Метаданные должны:



\- располагаться в начале документа;

\- использовать одинаковый порядок;

\- иметь единый формат оформления;

\- обновляться при каждом существенном изменении документа.



\---



\# 4. Heading Rules



Для всей документации используется единая иерархия заголовков.



\## H1



Используется только один раз.



Содержит название документа.



\---



\## H2



Используется для основных разделов документа.



Каждый раздел должен описывать самостоятельную область ответственности.



\---



\## H3



Используется для подразделов внутри H2.



\---



\## H4 и ниже



Используются только при объективной необходимости.



Избыточная вложенность ухудшает читаемость документации и не рекомендуется.



\---



\## Heading Principle



Структура документа должна быть плоской и предсказуемой.



Если раздел невозможно понять по заголовкам без чтения текста, структура считается недостаточно качественной.



\# 5. Writing Style



\## Purpose



Вся документация DevOS должна использовать единый инженерный стиль изложения.



Цель документации — максимально быстро и однозначно передавать информацию.



Документы не являются статьями, руководствами или маркетинговыми материалами.



\---



\## General Principles



Документация должна быть:



\- точной;

\- лаконичной;

\- последовательной;

\- однозначной;

\- легко читаемой.



Каждое предложение должно нести полезную информацию.



\---



\## Engineering Language



Предпочтение отдаётся инженерному языку.



Следует использовать:



\- факты;

\- определения;

\- правила;

\- ограничения;

\- принципы.



Избегать:



\- эмоциональных оценок;

\- художественных описаний;

\- субъективных выводов;

\- разговорных выражений.



\---



\## One Responsibility



Каждый раздел должен отвечать только за одну тему.



Если раздел начинает описывать несколько различных областей, его необходимо разделить.



\---



\## Short Paragraphs



Документация должна состоять из небольших смысловых блоков.



Рекомендуемый размер абзаца:



\- 2–5 предложений.



Слишком большие абзацы ухудшают восприятие информации.



\---



\## Active Voice



Предпочтительно использовать активную форму.



Например:



✔ "Модуль публикует событие."



вместо



✘ "Событие публикуется модулем."



\---



\## Avoid Ambiguity



Не допускаются формулировки:



\- возможно;

\- обычно;

\- иногда;

\- желательно;

\- скорее всего;

\- рекомендуется (если речь идёт об обязательном требовании).



Если правило обязательно, оно должно быть сформулировано однозначно.



\---



\# 6. Naming Conventions



\## Purpose



Единые правила именования обеспечивают предсказуемость всей документации.



\---



\## Document Names



Используется формат:



```

NN\_Name.md

```



где



NN — номер документа.



Пример:



```

08\_Database\_Design.md

```



\---



\## Section Names



Названия разделов оформляются в Pascal Case.



Например:



\- Purpose

\- Responsibilities

\- Architecture Overview

\- Engineering Principles



\---



\## Technical Terms



Во всей документации используются одинаковые названия.



Например:



Всегда использовать:



\- Module

\- Event

\- API

\- Aggregate

\- Domain

\- Entity

\- Service

\- Repository



Не допускается использование разных названий для одного и того же понятия.



\---



\## Product Terms



Все продуктовые сущности также должны иметь единое название.



Например:



если используется термин



```

Workspace

```



то нельзя в другом документе использовать:



\- Project Space;

\- Working Area;

\- Cabinet.



\---



\## Consistency Rule



Одно понятие — одно официальное название.



\---



\# 7. Tables Standard



\## Purpose



Таблицы используются тогда, когда информация легче воспринимается в структурированном виде.



\---



\## Recommended Usage



Таблицы рекомендуется использовать для:



\- сравнения;

\- справочной информации;

\- зависимостей;

\- списков документов;

\- матриц ответственности;

\- маршрутов навигации.



\---



\## Table Design



Каждая таблица должна иметь понятные заголовки.



Например:



| Column | Description |

|---------|-------------|



Не рекомендуется использовать таблицы с большим количеством пустых ячеек.



\---



\## Alternative



Если информация представляет собой последовательность действий, предпочтительно использовать список, а не таблицу.



\---



\# 8. Diagrams Standard



\## Purpose



Диаграммы используются только тогда, когда они упрощают понимание системы.



\---



\## Preferred Style



До внедрения специализированных инструментов используется ASCII-графика.



Например:



```text

User



↓



Frontend



↓



Backend



↓



Database

```



или



```text

Module A

│

├── Service

│

├── Repository

│

└── Events

```



\---



\## Diagram Rules



Каждая схема должна:



\- читаться сверху вниз;

\- использовать единый стиль;

\- содержать только необходимую информацию;

\- не дублировать текст документа.



\---



\## Complexity



Одна схема должна описывать только одну идею.



Если схема становится слишком большой, её необходимо разделить.



\---



\# 9. Markdown Standard



\## Purpose



Вся документация DevOS оформляется в едином стиле Markdown.



\---



\## Lists



Используются маркированные списки:



\- первый пункт;

\- второй пункт;

\- третий пункт.



Нумерованные списки используются только для последовательности действий.



\---



\## Code Blocks



Все примеры кода оформляются через fenced code blocks.



Например:



```python

def example():

&#x20;   pass

```



\---



\## Tables



Используется стандартный Markdown-синтаксис.



\---



\## Quotes



Цитаты применяются только для выделения важных инженерных принципов.



\---



\## Bold



Жирный текст используется только для:



\- названий документов;

\- ключевых терминов;

\- важных инженерных правил.



Не рекомендуется злоупотреблять выделением.



\---



\## Markdown Principle



Разметка должна улучшать читаемость документа, а не усложнять её.



\# 10. Cross References



\## Purpose



Документы DevOS не существуют изолированно.



Каждый документ должен ссылаться только на действительно связанные материалы.



Это позволяет быстро переходить между связанными областями знаний без поиска по всей документации.



\---



\## Reference Rules



При упоминании документа всегда используется его официальное имя.



Правильно:



\- \*\*05A\_Architecture\_Rules.md\*\*

\- \*\*09\_API\_Design.md\*\*

\- \*\*11\_Security\_Model.md\*\*



Неправильно:



\- "смотри документ про API";

\- "архитектурный документ";

\- "документ безопасности".



\---



\## Reference Principle



Ссылка должна вести только на документ, который является официальным владельцем соответствующей информации.



Если тема описана в другом документе только частично, ссылка должна вести к основному источнику.



\---



\## Circular References



Допускаются взаимные ссылки между документами, если они отражают реальные зависимости.



Избыточные перекрёстные ссылки не рекомендуются.



\---



\# 11. Versioning Standard



\## Purpose



Все документы DevOS используют единый подход к управлению версиями.



Версия документа отражает масштаб изменений, а не количество правок.



\---



\## Version Format



Используется формат:



```

MAJOR.MINOR

```



Примеры:



```

1.0

1.1

1.2

2.0

```



\---



\## Minor Update



Версия увеличивается на MINOR при:



\- уточнении текста;

\- исправлении ошибок;

\- добавлении новых подразделов;

\- улучшении примеров;

\- обновлении ссылок.



\---



\## Major Update



Версия увеличивается на MAJOR при:



\- изменении структуры документа;

\- изменении инженерных решений;

\- изменении области ответственности;

\- существенном пересмотре содержания.



\---



\## Version Principle



Документ всегда должен содержать только одну актуальную версию.



История изменений хранится отдельно и не должна перегружать основное содержимое документа.



\---



\# 12. AI Documentation Rules



\## Purpose



Настоящие правила определяют, как AI должен создавать и изменять документацию DevOS.



\---



\## AI Must



AI обязан:



\- соблюдать настоящий стандарт;

\- использовать официальную терминологию DevOS;

\- придерживаться структуры документа;

\- поддерживать единый стиль;

\- сохранять архитектурную целостность документации.



\---



\## AI Must Not



AI не должен:



\- придумывать новые структуры без необходимости;

\- переименовывать существующие сущности;

\- изменять область ответственности документа;

\- переносить информацию между документами без причины;

\- создавать дублирование.



\---



\## AI Behaviour



Перед созданием нового документа AI обязан:



1\. определить категорию документа;

2\. выбрать подходящий шаблон;

3\. соблюдать единый стиль;

4\. использовать официальную терминологию;

5\. проверить взаимосвязи с существующей документацией.



\---



\## Engineering Rule



AI является редактором документации.



Он не является автором архитектурных решений.



\---



\# 13. Documentation Review Checklist



Перед завершением любого документа необходимо выполнить следующую проверку.



\## Structure



□ Использована стандартная структура.



□ Все обязательные разделы присутствуют.



\---



\## Terminology



□ Используются официальные термины DevOS.



□ Нет разных названий одной сущности.



\---



\## Quality



□ Нет дублирования информации.



□ Каждый раздел имеет одну ответственность.



□ Документ читается последовательно.



\---



\## References



□ Указаны связанные документы.



□ Нет ошибочных ссылок.



\---



\## Style



□ Используется инженерный стиль.



□ Нет разговорных выражений.



□ Нет субъективных оценок.



\---



\## Final Validation



□ Документ соответствует Documentation Standards.

\# 14. Common Mistakes



Наиболее распространённые ошибки при создании документации.



\---



\## Mixing Responsibilities



Нельзя описывать несколько независимых тем в одном документе.



\---



\## Information Duplication



Не допускается копирование одинаковой информации в разные документы.



\---



\## Inconsistent Terminology



Нельзя использовать разные названия одной и той же сущности.



\---



\## Overcomplicated Structure



Не рекомендуется создавать глубокую вложенность разделов без объективной необходимости.



\---



\## Missing Purpose



Каждый документ обязан чётко отвечать на вопрос:



> Зачем он существует?



\---



\## Missing References



Документ не должен существовать отдельно от общей системы документации.



\---

\- Metadata

\- Purpose

\- Responsibilities

\- Main Architecture

\- Engineering Principles

\- Related Documents

\- Final Statement



\---



\## Product Document



Рекомендуемая структура:



\- Metadata

\- Purpose

\- Business Goals

\- Functional Requirements

\- User Scenarios

\- Related Documents

\- Final Statement



\---



\## Development Document



Рекомендуемая структура:



\- Metadata

\- Purpose

\- Workflow

\- Rules

\- Best Practices

\- Related Documents

\- Final Statement



\---



\## AI Bootstrap Document



Рекомендуемая структура:



\- Metadata

\- Purpose

\- Context

\- Navigation / Rules

\- Final Statement



\---



\## Pattern Principle



Перед созданием нового документа необходимо выбрать наиболее подходящий шаблон.



Это обеспечивает единообразие всей документации.



\---



\# 16. Documentation Quality Criteria



Документ DevOS считается качественным, если он:



\- имеет одну область ответственности;

\- легко читается;

\- не содержит противоречий;

\- использует единую терминологию;

\- не дублирует другие документы;

\- легко обновляется;

\- помогает инженеру быстрее выполнять работу.



Качество документа определяется не его объёмом, а ясностью, структурой и практической пользой.



\---



\# 17. Final Statement



Documentation Standards является единым стандартом оформления всей документации DevOS.



Все новые документы проекта должны соответствовать настоящему стандарту.



Единый подход к структуре, терминологии, стилю и сопровождению обеспечивает:



\- предсказуемость документации;

\- лёгкость навигации;

\- высокое качество инженерных материалов;

\- эффективную работу инженеров и AI.



Настоящий документ является обязательной основой для дальнейшего развития всей документационной системы DevOS.
