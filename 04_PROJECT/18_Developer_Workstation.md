\# Назначение документа



\## Цель



Данный документ определяет официальный стандарт рабочей станции разработчика DevOS.



Любой человек или AI-агент, участвующий в разработке платформы, должен использовать рабочее окружение, соответствующее требованиям настоящего документа.



Основная задача документа — обеспечить полностью воспроизводимую, безопасную и одинаковую среду разработки независимо от компьютера, операционной системы или используемого AI-агента.



\---



\# Область применения



Настоящий документ распространяется на:



\- разработчиков DevOS;

\- архитекторов проекта;

\- AI coding agents, совместимых с `AGENTS.md` и официальной документацией DevOS.



Документ описывает:



\- требования к рабочей станции;

\- обязательное программное обеспечение;

\- требования к Git;

\- требования к GitHub;

\- требования к аутентификации;

\- правила взаимодействия AI с рабочим окружением;

\- процедуры проверки готовности рабочего места;

\- процедуры восстановления после переустановки системы или замены компьютера.



\---



\# Основные принципы



Рабочее место разработчика DevOS должно соответствовать следующим принципам.



\## 1. Полная воспроизводимость



Любая новая рабочая станция должна быть полностью подготовлена исключительно по документации проекта.



Если для настройки рабочего места требуется выполнить действия, отсутствующие в документации, документация считается неполной и должна быть обновлена.



\---



\## 2. Автоматизация



Все повторяющиеся действия должны выполняться средствами автоматизации.



Приоритет имеют:



\- Git;

\- GitHub CLI;

\- SSH;

\- терминал;

\- официальные CLI-инструменты.



Ручная настройка допускается только в тех случаях, когда автоматизация отсутствует.



\---



\## 3. Безопасность



Рабочее окружение не должно содержать открытых секретов.



Закрытые ключи, токены и учётные данные никогда не должны храниться внутри репозитория проекта.



Для аутентификации используются только безопасные механизмы:



\- SSH;

\- GitHub CLI;

\- официальные менеджеры учётных данных.



\---



\## 4. Поддержка AI-разработки



Рабочее место должно быть полностью совместимо с AI-агентами.



Любой официальный AI-инструмент должен иметь возможность:



\- читать документацию проекта;

\- работать с Git;

\- работать с GitHub;

\- выполнять команды терминала;

\- создавать и изменять файлы проекта;

\- запускать процессы разработки.



\---



\## 5. Единый стандарт



Независимо от того, кто работает над проектом — человек или AI, — все используют одинаковое рабочее окружение.



Это позволяет:



\- уменьшить количество ошибок;

\- исключить различия между разработчиками;

\- упростить сопровождение проекта;

\- сделать процесс разработки максимально предсказуемым.

Все изменения в настройке рабочего окружения должны вноситься только в соответствующий раздел данного документа.

\## Эталонная платформа



Все инструкции, примеры команд, процедуры настройки и документация проекта ориентированы на \*\*Windows 11\*\*.



При наличии различий между операционными системами именно реализация для Windows считается официальной.



Поддержка других платформ не потребует изменения архитектуры DevOS и будет добавляться по мере необходимости.

\# Требования к рабочей станции



Данный раздел описывает не конкретные модели оборудования, а минимальные функциональные требования, необходимые для комфортной разработки DevOS.



\---



\## Производительность



Рабочая станция должна обеспечивать одновременную работу следующих компонентов:



\- IDE;

\- AI-агента;

\- терминала;

\- локального backend;

\- frontend;

\- браузера;

\- документации проекта.



Недостаточная производительность рабочего компьютера существенно снижает эффективность работы AI и разработчика.



\---



\## Оперативная память



Рабочая станция должна иметь достаточный объём оперативной памяти для одновременного запуска всех необходимых инструментов разработки.



При увеличении количества сервисов DevOS требования к памяти могут возрастать.



\---



\## Накопитель



Рабочая станция должна использовать SSD.



На накопителе должно быть достаточно свободного пространства для хранения:



\- репозиториев Git;

\- зависимостей проектов;

\- Docker-образов (при использовании);

\- локальных баз данных;

\- кэша IDE;

\- временных файлов AI-инструментов.



Использование HDD в качестве основного диска разработки не рекомендуется.



\---



\## Интернет-соединение



Для разработки требуется стабильное подключение к сети Интернет.



Рабочая станция должна иметь возможность постоянно обращаться к следующим сервисам:



\- GitHub;

\- пакетным менеджерам;

\- AI-провайдерам;

\- официальной документации используемых технологий.



\---



\## Терминал



Рабочая станция должна иметь современную командную оболочку.



Допускается использование:



\- Git Bash;

\- Windows Terminal;

\- PowerShell.



Терминал должен поддерживать выполнение всех официальных инструментов DevOS.



\---



\# Обязательные учётные записи



Для полноценной работы над проектом разработчик должен иметь следующие учётные записи.



| Сервис | Обязательно | Назначение |

|---------|-------------|------------|

| GitHub | ✅ | Хранение исходного кода |

| Провайдер выбранного AI-инструмента | ⏳ | Требуется только при использовании соответствующего сервиса |

| Google | ⏳ | Будущие интеграции проекта |



Учётные записи, отмеченные как необязательные, становятся обязательными только при использовании соответствующих инструментов.



\---



\# Обязательное программное обеспечение



Следующее программное обеспечение входит в официальный стандарт рабочей станции DevOS.



| Программа | Обязательно | Назначение |

|------------|-------------|------------|

| Git | ✅ | Система контроля версий |

| GitHub CLI | ✅ | Работа с GitHub через терминал |

| Git Bash / Windows Terminal | ✅ | Командная строка |

| Visual Studio Code | ✅ | Основная среда разработки |

| Совместимый AI coding agent | ✅ | Выполнение задач по `AGENTS.md` и профильной документации |

| Docker Desktop | ⏳ | Контейнеризация |

| Python | ⏳ | Backend-разработка |

| Node.js | ⏳ | Frontend-разработка |



По мере развития DevOS данный список может расширяться.



\---



\# Политика установки программного обеспечения



На рабочую станцию устанавливается только то программное обеспечение, которое используется в текущем этапе разработки.



Не допускается установка большого количества инструментов "на будущее", если они не используются проектом.



Такой подход обеспечивает:



\- простоту обслуживания рабочего окружения;

\- минимизацию конфликтов между программами;

\- предсказуемость поведения среды разработки;

\- лёгкое воспроизведение рабочего места на новом компьютере.



Любое новое программное обеспечение становится частью официального стандарта только после обновления настоящего документа.

\---



\# Стандарт настройки Git



Git является обязательной системой контроля версий для всех проектов DevOS.



Любой репозиторий, входящий в экосистему DevOS, должен использовать единые правила настройки Git.



Изменение данных правил допускается только после обновления официальной документации проекта.



\---



\## Настройка имени разработчика



Перед началом работы необходимо указать имя владельца Git-конфигурации.



Команда:



```bash

git config --global user.name "Имя Фамилия"

```



Пример:



```bash

git config --global user.name "Dmitry Klyuchkov"

```



\---



\## Настройка электронной почты



В DevOS используется официальный GitHub NoReply Email.



Это позволяет:



\- сохранить конфиденциальность личной почты;

\- корректно связывать коммиты с аккаунтом GitHub;

\- избежать проблем при публикации репозиториев.



Команда:



```bash

git config --global user.email "username@users.noreply.github.com"

```



Пример:



```bash

git config --global user.email "308893143+dima-AIi@users.noreply.github.com"

```



\---



\## Проверка конфигурации



После настройки рекомендуется проверить параметры Git.



Команда:



```bash

git config --global --list

```



Результат должен содержать как минимум:



```

user.name

user.email

```



\---



\## Основная ветка



Во всех репозиториях DevOS основной веткой считается



```

main

```



Использование других названий главной ветки допускается только по архитектурному решению проекта.



\---



\## Переносы строк



Для Windows рекомендуется использовать следующую настройку.



```bash

git config --global core.autocrlf true

```



Это позволяет автоматически корректно обрабатывать переносы строк между различными операционными системами.



\---



\# Стандарт SSH



Все репозитории DevOS используют SSH-аутентификацию.



Использование HTTPS допускается только как временное решение.



\---



\## Алгоритм ключа



Официальным алгоритмом является



```

ed25519

```



Использование других алгоритмов допускается только при наличии технической необходимости.



\---



\## Один компьютер — один SSH-ключ



Каждая рабочая станция должна иметь собственный SSH-ключ.



Не допускается:



\- копирование приватных ключей между компьютерами;

\- использование одного SSH-ключа на нескольких рабочих станциях;

\- передача приватного ключа другим пользователям.



\---



\## Хранение ключей



По умолчанию SSH-ключи располагаются в каталоге



```

\~/.ssh/

```



Стандартная структура:



```

\~/.ssh/



id\_ed25519

id\_ed25519.pub

known\_hosts

```



Описание файлов:



| Файл | Назначение |

|------|------------|

| id\_ed25519 | Приватный ключ |

| id\_ed25519.pub | Публичный ключ |

| known\_hosts | Список доверенных серверов |



\---



\## Правила безопасности



Приватный ключ:



```

id\_ed25519

```



никогда не должен:



\- попадать в Git;

\- отправляться по электронной почте;

\- храниться в облаке;

\- передаваться другим людям.



Публичный ключ



```

id\_ed25519.pub

```



может свободно публиковаться и добавляться в GitHub.



\---



\## Проверка SSH



Проверка подключения выполняется командой



```bash

ssh -T git@github.com

```



Корректный результат:



```

Hi <username>!

You've successfully authenticated,

but GitHub does not provide shell access.

```



Данное сообщение означает:



\- SSH работает корректно;

\- GitHub распознал ключ;

\- рабочая станция готова к работе.



\---



\# Стандарт GitHub CLI



GitHub CLI является официальным инструментом автоматизации DevOS.



Через него выполняются:



\- создание репозиториев;

\- клонирование;

\- Pull Request;

\- управление ветками;

\- управление релизами;

\- автоматизация AI-агентов.



\---



\## Авторизация



Авторизация выполняется командой



```bash

gh auth login

```



После успешной настройки рекомендуется проверить состояние.



```bash

gh auth status

```



Корректный результат должен содержать:



\- активный аккаунт;

\- Git protocol: SSH;

\- необходимые права доступа.



\---



\## Используемый протокол



Во всех проектах DevOS используется



```

SSH

```



GitHub CLI также должен работать через SSH.



\---



\## Создание репозиториев



При наличии необходимых прав GitHub CLI может самостоятельно создавать новые репозитории.



Пример:



```bash

gh repo create DevOS --private

```



Конкретная последовательность создания и подключения репозитория определяется профильным `03_DEVELOPMENT/17_Project_Initialization.md`.

Для существующего локального проекта DevOS применяется local-first сценарий. Clone-first сценарий к текущему проекту не применяется.

AI выполняет создание репозитория, настройку remote, commit и push только в рамках отдельной задачи владельца проекта.



\---



\## Видимость репозиториев



По умолчанию все репозитории DevOS создаются как



```

Private

```



Публикация открытого репозитория выполняется только после отдельного решения владельца проекта.



\---



\# Стандарт именования репозиториев



Имя репозитория должно быть:



\- коротким;

\- понятным;

\- стабильным;

\- отражающим назначение проекта.



Примеры:



```

DevOS



DevOS-Backend



DevOS-Frontend



DevOS-Mobile



DevOS-Documentation

```



Не рекомендуется использовать:



```

DevOS2



NewDevOS



Project-Test



TempProject

```



Имя репозитория должно оставаться актуальным на протяжении всего жизненного цикла проекта.

\---



\# Работа AI-агентов



DevOS разрабатывается с использованием AI-агентов.



AI рассматривается как полноценный участник процесса разработки, однако не является архитектором проекта и не принимает архитектурные решения самостоятельно.



Основной задачей AI является ускорение разработки при строгом соблюдении утверждённой документации.



\---



\# Поддерживаемые AI-агенты



Допускается использование любого AI coding agent, который способен соблюдать корневой `AGENTS.md`, читать официальную документацию и работать в установленных владельцем границах задачи.

Конкретный AI-инструмент не является частью архитектуры DevOS и не получает отдельного операционного регламента.



Появление новых AI не требует изменения архитектуры проекта.



Если новый инструмент соответствует требованиям настоящего документа, он может использоваться в разработке.



\---



\# Основные обязанности AI



AI должен:



\- понимать структуру проекта;

\- соблюдать архитектуру DevOS;

\- использовать только утверждённые технологии;

\- работать исключительно в рамках поставленной задачи;

\- предлагать улучшения только после объяснения их пользы;

\- поддерживать единый стиль проекта.



Главная цель AI — помогать разработчику, а не принимать решения вместо него.



\---



\# Что AI обязан сделать перед началом работы



Перед выполнением любой задачи AI должен:



1\. Ознакомиться с контекстом проекта.

2\. Понять архитектуру DevOS.

3\. Найти документы, относящиеся к текущей задаче.

4\. Проверить существующую реализацию.

5\. Только после этого приступать к изменению кода.



Если контекста недостаточно, AI обязан сообщить об этом, а не делать предположения.



\---



\# Приоритет источников информации



При возникновении противоречий AI должен использовать следующий порядок приоритета.



1\. Документация DevOS.

2\. Исходный код проекта.

3\. Последние инструкции владельца проекта.

4\. Внешние источники.



Если внешний источник противоречит документации DevOS, приоритет имеет документация проекта.



\---



\# Работа с документацией



Перед изменением любой части проекта AI должен определить, какие документы относятся к текущей задаче.



Например:



Изменение архитектуры модуля:



→ читать раздел `01\_ARCHITECTURE`.



Изменение интерфейса:



→ читать раздел `02\_PRODUCT`.



Изменение процесса разработки:



→ читать раздел `03\_DEVELOPMENT`.



Работа без изучения соответствующей документации считается нарушением процесса разработки.



\---



\# Работа с Git



AI может выполнять Git-операции только в рамках текущего репозитория.



Допускается:



\- создание веток;

\- просмотр истории;

\- создание коммитов;

\- просмотр различий;

\- слияние изменений (если это входит в поставленную задачу).



AI не должен удалять историю Git или выполнять разрушительные команды без явного разрешения.



\---



\# Работа с GitHub



При наличии авторизации через GitHub CLI AI может:



\- создавать новые репозитории;

\- клонировать существующие;

\- создавать Pull Request;

\- управлять ветками;

\- публиковать изменения.



По умолчанию новые репозитории создаются приватными.



\---



\# Работа с терминалом



AI может использовать терминал для:



\- запуска проекта;

\- установки зависимостей;

\- выполнения тестов;

\- запуска Docker;

\- работы с Git;

\- работы с GitHub CLI.



Все команды должны соответствовать текущему этапу разработки.



\---



\# Ограничения



AI запрещается:



\- самостоятельно менять архитектуру проекта;

\- изменять структуру документации;

\- заменять технологии без согласования;

\- удалять документы проекта;

\- добавлять сторонние библиотеки без необходимости;

\- выполнять потенциально опасные команды без подтверждения.



Если существует несколько вариантов решения, AI обязан объяснить различия и дождаться выбора.



\---



\# Принцип минимальных изменений



AI должен вносить только те изменения, которые необходимы для выполнения текущей задачи.



Запрещается:



\- массовое форматирование файлов без необходимости;

\- изменение чужого кода вне области задачи;

\- рефакторинг, не связанный с поставленной задачей.



Минимальные изменения упрощают проверку и уменьшают вероятность появления ошибок.
