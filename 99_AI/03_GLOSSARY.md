# 03_GLOSSARY.md



**Status:** Draft



**Version:** 1.0



**Category:** AI Bootstrap



\---



\# Purpose



Glossary является официальным словарём терминов проекта DevOS.



Его задача — обеспечить единое понимание инженерных, архитектурных, продуктовых и технических терминов всеми участниками проекта.



Настоящий документ используется:



\- инженерами;

\- архитекторами;

\- AI-системами;

\- новыми участниками проекта.



Glossary не заменяет профильную документацию.



Он содержит краткие определения и указывает единое значение каждого термина.



\---



\# 1. Glossary Philosophy



\## Single Meaning



Каждый термин DevOS имеет только одно официальное значение.



Использование разных определений одного и того же понятия не допускается.



\---



\## Single Name



Каждая сущность проекта имеет одно официальное название.



Например:



\- Module

\- Workspace

\- Event

\- Repository



Во всей документации используются именно эти названия.



\---



\## Documentation Consistency



Все документы DevOS обязаны использовать терминологию настоящего словаря.



Если возникает новый термин, он сначала добавляется в Glossary, после чего может использоваться в остальных документах.



\---



\## No Synonyms



Внутри инженерной документации не используются синонимы.



Это исключает неоднозначность при чтении документации человеком и AI.



\---



\## Engineering First



Определения ориентированы на инженерную практику.



Glossary не является энциклопедией.



Каждое определение должно быть:



\- коротким;

\- точным;

\- достаточным для разработки.



\---



\# 2. Core Platform Terms



\## DevOS



Главная программная платформа проекта.



Объединяет все архитектурные, продуктовые и инженерные компоненты системы.



\---



\## Platform



Совокупность всех сервисов, модулей и инфраструктуры DevOS.



\---



\## Workspace



Основная рабочая область пользователя внутри платформы.



Workspace является базовой единицей организации пользовательской деятельности.



Во всей документации используется только термин \*\*Workspace\*\*.



\---



\## Project



Отдельная единица работы внутри Workspace.



Project содержит задачи, данные и настройки, относящиеся к конкретной работе.



\---



\## Module



Самостоятельный функциональный блок системы, имеющий одну область ответственности.



Каждый модуль должен быть максимально независим от остальных.



\---



\## Service



Компонент, реализующий конкретную бизнес-логику или инфраструктурную функцию.



Service не является модулем.



\---



\## Component



Минимальная переиспользуемая часть системы.



Чаще всего используется применительно к пользовательскому интерфейсу.



\---



\# 3. Architecture Terms



\## Domain



Предметная область, описывающая часть бизнес-логики платформы.



\---



\## Aggregate



Группа связанных объектов предметной области, рассматриваемых как единое целое при выполнении операций.



\---



\## Entity



Объект предметной области, имеющий собственную идентичность.



Даже при изменении состояния Entity остаётся тем же объектом.



\---



\## Value Object



Объект, определяемый исключительно своими значениями.



Не имеет собственной идентичности.



\---



\## Repository



Компонент, отвечающий за получение и сохранение сущностей.



Repository не содержит бизнес-логику.



\---



\## Service Layer



Уровень приложения, реализующий бизнес-процессы с использованием доменных объектов.



\---



\## Adapter



Компонент, преобразующий взаимодействие между внутренними и внешними интерфейсами системы.



\---



\## Infrastructure



Все технические компоненты, обеспечивающие работу платформы, но не относящиеся к бизнес-домену.



Например:



\- база данных;

\- очередь сообщений;

\- файловое хранилище;

\- внешние API.



\# 4. Backend Terms



\## Backend



Серверная часть платформы, отвечающая за выполнение бизнес-логики, обработку запросов, управление данными и взаимодействие с внешними сервисами.



\---



\## Endpoint



Конкретная точка доступа API.



Каждый Endpoint отвечает за выполнение одной операции.



Пример:



```

POST /projects

GET /users/{id}

```



\---



\## Controller



Компонент Backend, принимающий HTTP-запрос, выполняющий первичную обработку и передающий выполнение соответствующему сервису.



Controller не должен содержать бизнес-логику.



\---



\## DTO (Data Transfer Object)



Объект, предназначенный исключительно для передачи данных между слоями приложения или между клиентом и сервером.



DTO не содержит бизнес-поведения.



\---



\## Request



Структура входящих данных, получаемых сервером от клиента.



\---



\## Response



Структура данных, возвращаемая сервером клиенту после выполнения операции.



\---



\## Middleware



Компонент, выполняющий дополнительную обработку запроса до или после основной логики.



Типичные задачи Middleware:



\- аутентификация;

\- логирование;

\- проверка прав доступа;

\- обработка ошибок.



\---



\## Dependency Injection (DI)



Механизм передачи зависимостей объекту извне вместо их самостоятельного создания.



Используется для уменьшения связанности компонентов.



\---



\## Transaction



Последовательность операций с данными, которая выполняется как единое целое.



Все изменения либо успешно фиксируются, либо полностью отменяются.



\---



\# 5. Database Terms



\## Database



Основное хранилище данных платформы.



\---



\## Table



Структура хранения однотипных записей.



Каждая таблица отвечает за один тип сущностей.



\---



\## Record



Отдельная строка таблицы.



Представляет экземпляр конкретной сущности.



\---



\## Column



Поле записи, содержащее одно конкретное значение.



\---



\## Primary Key



Поле, однозначно идентифицирующее запись.



\---



\## Foreign Key



Поле, связывающее запись с другой таблицей.



Используется для построения отношений между сущностями.



\---



\## Index



Дополнительная структура данных, ускоряющая поиск записей.



Индексы используются только при наличии практической необходимости.



\---



\## Migration



Последовательность изменений структуры базы данных.



Каждая миграция должна быть воспроизводимой и обратимой, если это возможно.



\---



\## Constraint



Правило, ограничивающее допустимые значения данных.



Например:



\- NOT NULL;

\- UNIQUE;

\- CHECK;

\- FOREIGN KEY.



\---



\## Relation



Логическая связь между двумя сущностями базы данных.



\---



\# 6. API Terms



\## API



Интерфейс взаимодействия между программными компонентами.



В DevOS используется REST API как основной способ обмена данными.



\---



\## REST



Архитектурный стиль построения сетевых интерфейсов.



\---



\## Resource



Объект предметной области, доступный через API.



Например:



\- User

\- Project

\- Workspace



\---



\## Payload



Данные, передаваемые внутри HTTP-запроса или ответа.



\---



\## Authentication



Процесс подтверждения личности пользователя или сервиса.



Отвечает на вопрос:



> Кто выполняет запрос?



\---



\## Authorization



Процесс проверки прав пользователя.



Отвечает на вопрос:



> Что разрешено выполнять?



\---



\## Idempotency



Свойство операции многократного выполнения с одинаковым результатом.



Например:



```

PUT

DELETE

```



\---



\## Pagination



Механизм постраничной выдачи больших наборов данных.



\---



\## Rate Limit



Ограничение количества запросов за определённый промежуток времени.



Используется для защиты платформы от перегрузки.



\---



\# 7. Event Terms



\## Event



Факт наступления значимого действия внутри системы.



Event сообщает, что событие произошло.



\---



\## Domain Event



Событие, относящееся к предметной области приложения.



Используется внутри бизнес-домена.



\---



\## Integration Event



Событие, предназначенное для взаимодействия между различными сервисами или внешними системами.



\---



\## Event Bus



Компонент, обеспечивающий доставку событий подписчикам.



\---



\## Publisher



Компонент, публикующий событие.



\---



\## Subscriber



Компонент, подписанный на получение определённого типа событий.



\---



\## Event Handler



Компонент, выполняющий обработку полученного события.



\---



\## Queue



Очередь сообщений, обеспечивающая асинхронную обработку событий.



Используется для повышения масштабируемости и отказоустойчивости.



\---



\# 8. Security Terms



\## User



Пользователь платформы DevOS.



\---



\## Role



Набор разрешений, объединённых в логическую группу.



Например:



\- Administrator;

\- Manager;

\- Member.



\---



\## Permission



Минимальная единица права доступа.



Permission определяет возможность выполнения конкретного действия.



\---



\## Policy



Правило проверки доступа, объединяющее несколько Permission.



\---



\## RBAC



Role-Based Access Control.



Модель управления доступом, основанная на ролях.



\---



\## JWT



JSON Web Token.



Компактный токен, содержащий информацию о пользователе и его правах.



\---



\## Session



Период взаимодействия пользователя с системой после успешной аутентификации.



\---



\## Access Token



Краткоживущий токен, используемый для выполнения запросов к API.



\---



\## Refresh Token



Долгоживущий токен, предназначенный для получения нового Access Token без повторной аутентификации.



\---



\## Least Privilege Principle



Принцип минимально необходимых привилегий.



Каждый пользователь получает только те права, которые необходимы для выполнения его задач.



\# 9. Product Terms



\## Feature



Отдельная функциональная возможность платформы, предоставляющая ценность пользователю.



Feature может состоять из нескольких User Story и затрагивать несколько модулей системы.



\---



\## MVP (Minimum Viable Product)



Минимально жизнеспособная версия продукта, содержащая только необходимую функциональность для достижения поставленной бизнес-цели.



\---



\## User Story



Краткое описание пользовательской потребности.



User Story определяет:



\- кто выполняет действие;

\- что требуется выполнить;

\- какую ценность получает пользователь.



\---



\## Epic



Крупная функциональная область, объединяющая несколько User Story.



\---



\## Task



Конкретная инженерная работа, необходимая для реализации функциональности.



Task является минимальной единицей планирования разработки.



\---



\## Milestone



Контрольная точка проекта, обозначающая достижение важного результата.



\---



\## Roadmap



План развития продукта, определяющий последовательность реализации функциональности.



Roadmap описывает направление развития, а не техническую реализацию.



\---



\# 10. AI Terms



\## AI Bootstrap



Набор документов, позволяющий AI быстро понять устройство проекта и начать работу.



\---



\## Context



Совокупность информации, необходимой AI для принятия решений.



Контекст включает:



\- архитектуру;

\- терминологию;

\- правила;

\- ограничения;

\- цели проекта.



\---



\## Session



Непрерывный процесс взаимодействия AI с пользователем в рамках одной задачи.



\---



\## Prompt



Инструкция, определяющая задачу AI.



Prompt не является частью архитектуры DevOS.



\---



\## Knowledge Source



Официальный документ проекта, используемый AI как источник информации.



AI обязан отдавать приоритет информации из документации, а не собственным предположениям.



\---



\## Documentation Owner



Документ, являющийся официальным владельцем определённой информации.



Например:



\- API → `09\_API\_Design.md`

\- Security → `11\_Security\_Model.md`



\---



\## Engineering Decision



Решение, принимаемое на основе архитектуры, документации и инженерных принципов проекта.



\---



\# 11. Naming Rules



\## One Object — One Name



Каждая сущность DevOS имеет одно официальное название.



Это название используется во всей документации.



\---



\## Stable Terminology



После утверждения термин не должен изменяться без веской причины.



Изменение терминологии требует обновления всей документации проекта.



\---



\## English Technical Terms



Основные инженерные термины используются на английском языке.



Например:



\- Module

\- Service

\- Event

\- Repository

\- Workspace

\- Aggregate



Это соответствует отраслевой практике и снижает неоднозначность.



\---



\## Context Before Translation



Если английский термин уже является общепринятым в инженерной среде, он не переводится.



Например:



Используется:



\- API

\- Backend

\- Frontend

\- Middleware

\- DTO



\---



\# 12. Forbidden Synonyms



Во избежание неоднозначности запрещается использовать разные названия для одной сущности.



| Не использовать | Использовать |

|-----------------|-------------|

| Кабинет | Workspace |

| Рабочая область | Workspace |

| Пространство проекта | Workspace |

| Контроллер API | Controller |

| Хранилище | Repository |

| Модуль сервиса | Module |

| Сообщение | Event (если речь о событии системы) |

| Пользовательская роль доступа | Role |

\# 15. Glossary Maintenance



Glossary обновляется при появлении:



\- новой архитектурной сущности;

\- нового инженерного понятия;

\- нового продуктового термина;

\- нового обязательного сокращения.



Удаление терминов допускается только после удаления соответствующей сущности из проекта.



\---



\## Maintenance Rule



Перед использованием нового термина он должен быть зарегистрирован в настоящем словаре.

\# 17. Final Statement



Glossary является официальным словарём терминологии DevOS.



Все инженерные, архитектурные, продуктовые и AI-документы обязаны использовать определения, приведённые в настоящем документе.



Поддержание единой терминологии обеспечивает:



\- отсутствие неоднозначности;

\- единообразие документации;

\- корректную работу AI;

\- быстрое понимание проекта новыми инженерами;

\- долгосрочную сопровождаемость платформы.



При возникновении новых терминов они должны быть сначала добавлены в Glossary и только после этого использоваться в остальных документах проекта.
